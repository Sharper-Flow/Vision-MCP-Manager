# ADR 0001: MCP 2026-07-28 alignment

- **Status:** Accepted
- **Date:** 2026-07-20

## Context

Vision currently implements the MCP Streamable HTTP session lifecycle used by
the 2025-03-26 protocol revision. A client initializes, receives an
`Mcp-Session-Id`, sends `notifications/initialized`, and reuses that session ID
for later requests. Vision then gives each client session an isolated downstream
subprocess.

The [MCP 2026-07-28 release candidate][mcp-rc] changes that transport model:

- protocol-level `initialize` / `initialized` and `Mcp-Session-Id` are removed;
- requests become stateless at the transport layer;
- [SEP-2243][sep-2243] requires `Mcp-Method` and, where applicable,
  `Mcp-Name` HTTP headers so gateways can route and govern calls without
  inspecting JSON bodies;
- namespace work such as SEP-993 is converging on explicit, collision-safe tool
  grouping.

Vision must preserve its process-isolation value without allowing its client,
proxy, and guidance surfaces to drift from the protocol.

## Decision

### Retain downstream isolation as a Vision capability

Vision will retain process-per-client isolation where configured. Under a
stateless MCP transport, this is an implementation and safety capability—not a
claim that protocol sessions still exist. Vision may mint its own explicit,
bounded routing handles when a stateful downstream requires affinity.

This preserves:

- crash blast-radius isolation;
- independent lifecycle and resource limits for stateful upstream MCP servers;
- transparent respawn after a downstream process exits.

### Split SEP-2243 ownership at the HTTP boundary

- **Outbound OpenCode plugin client:** the hand-written client owns emission of
  `Mcp-Method` and applicable `Mcp-Name` headers. It cannot delegate this to an
  SDK it does not use.
- **Inbound Vision daemon:** the Go MCP SDK integration owns header validation,
  body/header consistency checks, and routing exposure when the SDK supports
  the finalized protocol.

Outbound support should land first or alongside inbound enforcement so an
upgraded daemon does not reject the current plugin.

### Keep one tool-name derivation boundary

Code Mode names are derived in the guidance helper that maps canonical tool
names to `tools.<namespace>.<tool>` or bracket notation. If the namespace work
represented by SEP-993 stabilizes around `<namespace>__<tool>`, that helper is
the single extension point. Catalog and documentation must not invent separate
normalization rules.

### Migration trigger

Vision will begin the stateless transport migration only when all three are
true:

1. MCP 2026-07-28 (or its successor) is final;
2. Vision's Go MCP SDK supports the finalized stateless lifecycle and required
   HTTP headers;
3. at least one supported downstream client requires the new revision.

Until then, the plugin targets 2025-03-26, validates version negotiation, and
uses bounded session recovery.

## Consequences

### Positive

- Vision keeps its differentiating process isolation without misrepresenting it
  as future protocol state.
- Header ownership is explicit on both sides of the proxy boundary.
- Code Mode and future namespace naming evolve through one structural helper.
- Migration has a testable trigger instead of following an SDK upgrade
  implicitly.

### Negative

- Vision temporarily supports two concepts: protocol sessions today and
  Vision-managed routing/isolation after the stateless migration.
- The hand-written plugin client must carry transport conformance tests until it
  is removed or replaced.
- A future migration will require coordinated plugin, daemon, proxy, and
  compatibility-test changes.

## Verification requirements

- Pin current plugin lifecycle behavior with initialize, negotiation, session,
  SSE/JSON, and retry tests.
- Add outbound header tests before enabling daemon-side SEP-2243 enforcement.
- Add compatibility tests for current and stateless clients during migration.
- Preserve the process-isolation test suite independently of transport-session
  tests.
